1. ЦЕЛЬ ПРОЕКТА

Клиент выбирает услугу, мастера, дату и свободное время,
подтверждает запись, видит свои записи и может отменить будущую.

Администратор управляет:
- Услугами и ценами.
- Мастерами и списком оказываемых ими услуг.
- Рабочими часами, перерывами и отсутствиями.
- Записями клиентов.

Главный критерий:
если два клиента одновременно бронируют пересекающееся время
одного мастера, создаётся только одна запись. Второй клиент
получает понятное сообщение и может выбрать другое время.

Первая версия:
- Одна парикмахерская.
- Одна услуга и один мастер в каждой записи.
- Две роли: CUSTOMER и ADMIN.
- Мастер — отдельная сущность без аккаунта и личного кабинета.
- Интерфейс на русском языке.
- Валюта и часовой пояс задаются настройками проекта.
- Для демо используй KZT и Asia/Almaty как заменяемые настройки.

За пределами MVP:
- Онлайн-оплата.
- SMS, email и Telegram-уведомления.
- Аналитика выручки.
- Несколько филиалов.
- Личный кабинет мастера.
- Лист ожидания.
- Несколько услуг или мастеров в одной записи.
- Учёт расходных материалов, кресел и другого оборудования.
- Перенос записи: клиент отменяет старую и создаёт новую.

- Моменты времени хранятся как timestamptz.
- Регулярное расписание хранится как локальное время салона.
- История записей сохраняется.
- Используемые услуги и мастера деактивируются вместо удаления.
- Изменение цены и длительности не меняет существующие записи.
- Деактивация запрещает новые записи, сохраняя существующие.
- Добавь индексы, внешние ключи и ограничения корректности.
- Не используй float для хранения денежных сумм.

6. РАСЧЁТ СВОБОДНОГО ВРЕМЕНИ

Источник истины — backend.
Frontend отображает полученные от API слоты.

Параметры запроса:
serviceId, masterId, date в формате YYYY-MM-DD.

Алгоритм:
1. Проверить активность услуги и мастера.
2. Проверить, что мастер оказывает выбранную услугу.
3. Определить день недели в часовом поясе парикмахерской.
4. Загрузить рабочее окно, перерывы и отсутствия.
5. Загрузить занятые интервалы.
6. Сформировать возможные начала с шагом 15 минут
   относительно начала рабочего окна.
7. Рассчитать endsAt и occupiedUntil.
8. Исключить недоступные варианты.

Правила:
- До начала должно оставаться минимум 30 минут.
- Горизонт записи — ближайшие 60 календарных дней.
- Весь интервал с буфером помещается в рабочие часы.
- Запись не пересекает перерыв, отсутствие и другую запись.
- Отменённая запись не занимает время.
- Занятость другого мастера не влияет на выбранного.
- Рабочие окна в MVP не переходят через полночь.

Используй полуоткрытые интервалы [start, end).
Если занятость заканчивается в 11:00, следующая запись
может начаться ровно в 11:00.

Пример:
женская стрижка длится 60 минут, буфер — 15 минут.
При начале в 10:00:
- endsAt = 11:00.
- occupiedUntil = 11:15.
- Следующая запись возможна с 11:15.

Пример длительной услуги:
окрашивание длится 150 минут, буфер — 15 минут.
При начале в 14:00 мастер занят до 16:45.

Не округляй незаметно присланное клиентом время.
Начало должно соответствовать допустимому слоту.

API принимает временные моменты с явным UTC offset или Z.
Календарь и подписи времени показывают часовой пояс салона,
даже если браузер клиента находится в другом часовом поясе.

Не полагайся на часовой пояс сервера.
Явно обрабатывай неоднозначное и несуществующее локальное время.

Вынеси правила доступности в отдельный модуль.
Используй их и для получения слотов, и для создания записи.

7. КОНКУРЕНТНОЕ БРОНИРОВАНИЕ

Обязательна защита от пересекающихся записей в PostgreSQL.

Недостаточные меры:
- Отключение кнопки.
- Проверка на frontend.
- SELECT перед INSERT без защищённой транзакции.
- Mutex в памяти Node.js.
- UNIQUE(masterId, startsAt).

Создание записи:
1. Открыть транзакцию.
2. Заблокировать строку мастера через FOR UPDATE.
3. После получения блокировки повторно прочитать актуальные данные.
4. Проверить услугу, расписание, перерывы, буфер и пересечения.
5. Рассчитать цену и границы интервала на сервере.
6. Создать CONFIRMED-запись.
7. Зафиксировать транзакцию.

При READ COMMITTED повторная проверка после ожидания
должна видеть уже зафиксированную запись конкурента.

Согласованный протокол блокировок применяется также к:
- Отмене записи.
- Изменению рабочих часов.
- Изменению перерывов и отсутствий.
- Изменению доступности услуг мастера.

Изменения услуг согласуй с бронированием и сохранением снимков.
Для нескольких блокировок определи единый порядок их получения.

Дополнительно реализуй ограничение PostgreSQL:
- Расширение btree_gist.
- EXCLUDE USING gist по равенству masterId и пересечению
  tstzrange(startsAt, occupiedUntil, '[)').
- Ограничение действует на неотменённые записи.
- Границы интервала обязательны и проходят CHECK-проверки.

Если Prisma не описывает ограничение декларативно,
создай его SQL-кодом в версионируемой миграции.

Конфликт возвращает HTTP 409:
{
  "code": "SLOT_UNAVAILABLE",
  "message": "Это время уже занято. Выберите другой слот."
}

Обработай соответствующее нарушение ограничения БД.
Не маскируй остальные ошибки базы под конфликт бронирования.

После 409 frontend:
- Сохраняет услугу, мастера и дату.
- Сбрасывает выбранное время.
- Обновляет доступность.
- Показывает понятное сообщение.

Защита должна работать при нескольких экземплярах NestJS.
Отображение свободного времени не создаёт временную бронь.

8. ОТМЕНА И РАСПИСАНИЕ

Клиент отменяет свою CONFIRMED-запись только до startsAt.

Повторная разрешённая отмена возвращает текущее состояние,
не меняя первоначальное время отмены.

После отмены интервал снова доступен.

Администратор:
- Создаёт записи для существующих клиентов.
- Подчиняется тем же ограничениям доступности.
- Отменяет будущие записи.
- Отмечает COMPLETED после endsAt.
- Не восстанавливает отменённую запись простой сменой статуса.

Если изменение расписания, перерыва или отсутствия
конфликтует с будущими CONFIRMED-записями:
- Отклони изменение с HTTP 409.
- Покажи конфликтующие записи администратору.
- Не перемещай и не отменяй клиентов автоматически.

10.2. КОМПОЗИЦИЯ СТРАНИЦ

На широких экранах используй общую контейнерную сетку
шириной примерно 1280–1440 px с боковыми полями 40–80 px.

Характерная композиция основных информационных секций:
- Слева 22–25% ширины: короткое название раздела.
- Справа 75–78%: описание, список услуг, фотографии или карточки.
- Между колонками тонкая вертикальная линия.
- Между секциями тонкие горизонтальные линии.
- Вертикальные границы продолжают общую сетку страницы.
- Внутренние отступы контентной колонки примерно 32–48 px.
- Между крупными секциями достаточно воздуха: 72–112 px.

Левые подписи: «О САЛОНЕ», «УСЛУГИ», «МАСТЕРА»,
«КАК ЗАПИСАТЬСЯ», «КОНТАКТЫ».
Это навигационные подписи секций, а не дополнительный заголовок
над каждой карточкой.

На mobile левая подпись переносится над контентом,
вертикальная разделительная линия убирается,
сетка становится одноколоночной, боковые поля — 16–20 px.

10.3. ФОН И ИЗОБРАЖЕНИЯ

В hero и заключительном блоке используй абстрактный halftone:
мелкие оранжевые точки разной заметности на чёрном фоне,
образующие крупные плавные волны или ленты, напоминающие
направление прядей волос. Между фигурами остаются чёрные поля.

Фон должен напоминать точечные формы на скриншотах,
а не обычный оранжевый градиент или светящийся размытый шар.
Реализация может использовать CSS-маски, SVG-паттерн или лёгкий
локальный растровый ресурс. WebGL и тяжёлые частицы не нужны.
Не создавай тысячи DOM-элементов ради точек.
Декор не перехватывает события и скрыт от скринридера.

Под формами, календарём, таблицами и основным текстом фон спокойный.

Фотографии относятся к парикмахерской:
- Портреты мастеров.
- Стрижки, укладки и окрашивание.
- Интерьер и рабочие детали.
Используй согласованный свет и обработку; волосы и результат
работы должны быть хорошо видны, без чрезмерного затемнения.
Для карточек мастеров подходят портреты 3:4.
Все ресурсы должны иметь допустимые условия использования.
Вымышленных демо-мастеров и демонстрационные фото не выдавай
за реальную команду или реальные работы действующего салона.

Не вставляй приложенные скриншоты как фон готового сайта.
Не переноси водяные знаки Referest и интерфейс сайта-источника.

10.4. ГЛАВНАЯ СТРАНИЦА

Шапка:
- Слева небольшой словесный логотип FORMA.
- Навигация: «Услуги», «Мастера», «О салоне», «Контакты».
- Справа вход либо ссылка «Мои записи» и CTA «Записаться» со стрелкой.
- На desktop всё в одну строку; высота около 72–80 px.
- При недостатке места используй доступное мобильное меню.
- Если шапка фиксированная, она не закрывает якоря и focus.

Hero по композиции крупного скриншота:
- Большое слово FORMA слева, занимающее значительную часть ширины.
- Ниже короткая фраза: «Стрижки. Цвет. Ваш характер.»
- Описание: «Выберите услугу, мастера и удобное время онлайн.»
- Основная CTA «Записаться» со стрелкой вправо.
- На фоне чёрно-оранжевые точечные формы.
- Не центрируй всю композицию и не заменяй её типовым hero
  с текстом слева и произвольной карточкой справа.
- На обычном desktop-экране CTA видна без прокрутки;
  при увеличении масштаба допускается естественная прокрутка без обрезки.

О салоне:
- Слева название секции.
- Справа крупный короткий текст о стрижках, окрашивании и уходе,
  ниже фотография интерьера или работы мастера.
- Не придумывай годы работы, рейтинги, награды и количество клиентов.
- Не делай обязательный текст почти невидимым до прокрутки.

Услуги:
- Используй реальные услуги из API и их точную стоимость и длительность.
- В основной колонке — широкие прямоугольные строки или панели.
- Название и описание слева, цена и длительность хорошо заметны.
- Действие «Выбрать» открывает запись с выбранной услугой.
- Различия по длине волос видны в названии услуги.
- Цвет, отступы и границы напоминают страницу Services на скриншоте.

Мастера:
- Три портретные карточки на desktop, одна колонка на mobile.
- Фото, имя, краткое описание, оказываемые услуги и действие «Выбрать».
- Мастер заранее выбирается в форме; затем доступны только его услуги.
- В обычном сценарии сначала выбирается услуга, затем подходящий мастер.
- Если каталог услуги или мастер изменились, недопустимый выбор сбрасывается.

Как записаться:
- Четыре пронумерованных блока 01–04, номера оранжевые.
- «Услуга», «Мастер», «Дата и время», «Подтверждение».
- Короткие понятные пояснения без технической терминологии.
- Композиция 2×2 на desktop, вертикальный список на mobile.

Контакты и подвал:
- Чёткая сетка с адресом, часами работы и контактами из конфигурации.
- Демонстрационные контакты явно обозначены и не принадлежат
  случайным реальным людям или организациям.
- Большое слово FORMA как типографический элемент нижнего блока.
- Рабочие ссылки на услуги, мастеров, запись и личный кабинет.
- Не добавляй блог, AI-разделы и фиктивные юридические страницы
  ради повторения структуры исходного сайта.

10.5. ЗАПИСЬ, ВХОД И ЛИЧНЫЙ КАБИНЕТ

Страницы:
- Главная.
- Каталог услуг.
- Пошаговая запись.
- Вход и регистрация.
- «Мои записи».
- Админка.
- 404.
«О салоне», «Мастера» и «Контакты» могут быть секциями главной:
отдельные страницы для них в MVP не обязательны.

Основной сценарий записи:
1. Услуга: описание, цена, длительность.
2. Подходящий мастер.
3. Дата и свободное время.
4. Проверка деталей и подтверждение.

Гость может выбрать параметры. Перед подтверждением требуется вход.
После входа выбор сохраняется, доступность проверяется повторно.

Визуальное оформление записи:
- Общая тёмная палитра, прямоугольные поля и тонкие границы.
- Небольшой индикатор шагов 01–04 с активным оранжевым состоянием.
- На desktop основная форма слева, сводка записи справа.
- На mobile сводка складывается в компактный раскрываемый блок.
- Выбранная услуга и мастер отмечаются рамкой и текстом или иконкой.
- Время представлено сеткой кнопок достаточного размера.
- Выбранный слот имеет оранжевую заливку и контрастный текст.
- Недоступные варианты нельзя нажать; пояснение не зависит только от цвета.
- Не добавляй точечный узор под полями, временем и текстом ошибок.
- Не показывай клиенту названия API, HTTP-коды, транзакции и PostgreSQL.

Все состояния обязательны:
- Загрузка: skeleton, соответствующий будущему содержимому.
- Пусто: «На эту дату свободного времени нет» и выбор другой даты.
- Конфликт: «Это время уже занято. Выберите другой слот».
- Ошибка сети: понятное объяснение и действие повторной загрузки.
- Успех: подтверждение с услугой, мастером, датой, временем и ценой.

При 409 сохрани услугу, мастера и дату, сбрось время,
обнови слоты и покажи сообщение в контексте выбора времени.
Защити интерфейс от устаревших ответов при быстром переключении дат.
Во время отправки отключай повторное подтверждение.

Вход и регистрация:
- Компактная форма на тёмной поверхности.
- Подписи над полями, ошибки под полями.
- Кнопка показа пароля с доступным названием.
- Разрешены вставка пароля, автозаполнение и менеджеры паролей.

«Мои записи»:
- Предстоящие и прошедшие посещения.
- Услуга, мастер, дата, время, цена и текстовый статус.
- Отмена допустимой будущей записи через диалог подтверждения.
- После отмены список и доступность обновляются.

10.6. АДМИНИСТРАТИВНЫЙ ИНТЕРФЕЙС

Сохрани общие цвета, типографику и геометрию.
Используй компактную рабочую компоновку без гигантских заголовков
и фоновой графики за данными.

Разделы: «Записи», «Услуги», «Мастера», «Расписание».
Записи: фильтры, группировка по дате, пагинация и действия.
Услуги: редактирование цены, длительности, буфера и активности.
Мастера: профиль, активность и привязка услуг.
Расписание: рабочие окна, перерывы, отсутствия.
Конфликт изменения расписания показывает затронутые записи
и не теряет введённые администратором значения.

Используй таблицы и формы там, где они удобнее карточек.
На mobile допустима прокрутка конкретной таблицы,
но не горизонтальная прокрутка всей страницы.

10.7. СТРАНИЦА 404

По мотивам скриншота:
- Чёрный фон и оранжевый точечный декор.
- Крупные оранжевые цифры 404.
- Заголовок «Страница не найдена».
- Пояснение и рабочая кнопка «На главную».
- Общая шапка и подвал.
- На mobile контент перестраивается без обрезки цифр и кнопки.

10.8. АНИМАЦИИ, АДАПТИВНОСТЬ И ПРОВЕРКА

Скриншоты задают статическую композицию. Анимации ниже —
адаптация для проекта, а не утверждение о поведении исходного сайта.

- Hover/focus-переходы: примерно 150–220 мс.
- Стрелка CTA может сдвигаться вправо на 3–4 px.
- При появлении секции допустим небольшой сдвиг и fade 250–400 мс.
- Не задерживай доступ к кнопкам, формам и чтению текста.
- Не используй перехват прокрутки, магнитные кнопки,
  нестандартный курсор и обязательный загрузочный экран.
- Уважай prefers-reduced-motion; без JS контент не должен
  оставаться скрытым из-за начального состояния анимации.

Доступность:
- Контраст текста не ниже WCAG AA.
- Видимые границы и focus интерактивных элементов.
- Минимальная удобная зона нажатия около 44×44 px.
- Управление меню, календарём и диалогами с клавиатуры.
- Возврат focus после закрытия диалога, закрытие по Escape.
- Статусы и ошибки передаются не только цветом.
- Сообщения об ошибке и успехе доступны скринридеру.
- При увеличении до 200% основной сценарий остаётся доступен.

Проверь реальные страницы на ширинах 375, 768 и 1440 px.
Сделай скриншоты главной, выбора времени, личного кабинета и админки.
Визуально сравни главную с пользовательскими референсами:
масштаб типографики, чёрно-оранжевая палитра, левая колонка,
вертикальные и горизонтальные линии, прямоугольные CTA,
характер точечного фона и общий ритм отступов.

Основные действия работают с настоящим API.
Не используй localStorage как базу записей
и не подменяй backend моками в готовом приложении.
Не сокращай backend, миграции и конкурентные тесты ради оформления.

11. ТЕСТЫ

Unit-тесты доступности:
- Короткие и длительные услуги.
- Буфер после услуги.
- Перерывы, выходные и отсутствия.
- Рабочие часы.
- Минимальное время до записи.
- Горизонт бронирования.
- Частичные пересечения и соседние интервалы.
- Отменённые записи.
- Независимость мастеров.
- Часовой пояс.

Интеграционные и e2e-тесты:
- Регистрация, вход, logout.
- Запрет назначения себе ADMIN.
- Запрет просмотра и отмены чужой записи.
- Запрет административных действий клиенту.
- Запись, отмена и освобождение времени.
- Повторная отмена.
- Сохранение цены и длительности существующей записи.
- Запрет записи на услугу, которую мастер не оказывает.
- Запрет обхода расписания прямым запросом.
- Конфликтующие изменения расписания.
- Ограничение пересечений непосредственно в PostgreSQL.

Главный конкурентный тест:
1. Настоящая тестовая PostgreSQL.
2. Применены миграции.
3. Созданы мастер, услуга, расписание и два клиента.
4. Одновременно отправлены два запроса на один слот.
5. Получены ровно один 201 и один 409.
6. В БД ровно одна неотменённая запись.

Дополнительно:
- Разные начала с пересечением интервалов.
- 10 одновременных запросов на один слот.
- Одинаковое время у разных мастеров успешно бронируется.
- Два экземпляра NestJS с общей PostgreSQL корректно
  разрешают конфликт между собой.

Не используй моки БД или SQLite для конкурентных тестов.
Не превращай проверку в последовательную через одно соединение.

Playwright:
вход → услуга → мастер → время → подтверждение → отмена.

Изолируй тестовую БД.
Не очищай пользовательские или production-данные.
Управляй временем тестов для воспроизводимости.

12. ДЕМО И ГОТОВЫЙ РЕЗУЛЬТАТ

Seed:
- Один администратор.
- Два клиента.
- Три мастера с различающимися наборами услуг.
- Услуги:
  • Мужская стрижка — 30 минут.
  • Женская стрижка, короткие волосы — 45 минут.
  • Женская стрижка, длинные волосы — 60 минут.
  • Детская стрижка — 30 минут.
  • Укладка — 45 минут.
  • Окрашивание — 150 минут.
  • Уход за волосами — 60 минут.
- Буферы после услуг.
- Рабочие часы и перерывы.
- Пример отсутствия мастера.
- Будущие, прошедшие и отменённые записи.

Цены и имена вымышленные.
Даты демо формируются относительно даты запуска.
Повторный seed не создаёт дубликаты и не удаляет реальные данные.
Демо-пароли доступны только в demo/development-режиме.

Подготовь:
- README на русском.
- .env.example без секретов.
- Dockerfile для frontend и backend.
- Docker Compose с PostgreSQL, миграциями и health checks.
- Команды запуска, seed, сборки и тестирования.
- Swagger UI.
- ER-диаграмму.
- Описание архитектуры.
- Объяснение защиты от двойного бронирования.
- GitHub Actions с PostgreSQL для интеграционных тестов.
- Инструкцию развёртывания демо.
- Указание использованных референсов.

Порядок работы:
1. Проверь рабочий каталог и инструкции проекта.
2. Кратко зафиксируй архитектуру и допущения.
3. Реализуй БД, миграции и бронирование.
